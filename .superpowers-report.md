## What moves when a message appears — measured, not assumed

**SUPERSEDED by review — see "Revision (round 2)" at the end of this file.**
The Lab measurement below was taken at a 424px preview height taller than
this card's registered floor, and I characterised the case where the
`.card-head` auto-margin absorbs the shift as the common one. It is not: the
composed screen sizes this card at EXACTLY `rowSpan × --u` with no slack
(`shell/PanelCanvas.tsx` / `panelCanvas.ts`), so what I called the rare
floor-only edge case is the default for every operator who has not enlarged
the card. I also missed that `svc.store.error()` can change on reconnect
(`compose/services.ts`'s revision effect), not only at mount, so it CAN
coincide with the carriage moving. Gabe's decision, given the corrected
picture: move the message after the step list so nothing follows it and
nothing moves, ever, at any card size. Implemented and verified below.

The message row is `line-height: calc(4.5*u)` + `margin-bottom: calc(1*u)`
= 5.5u (22px at the default 1x scale, --u=4px) when it renders — the exact
size the old reservation always held. `.panel-body` is `display:flex;
flex-direction:column` and every child, `.shp-msg` included, is
`flex:0 0 auto` (app.css:4341) — a deterministic flex-column fact, not a
guess.

Verified live in the Card Lab (dev server on my own worktree's port 5199,
`#/cards`, "Shaping" pill, "Shaping measured" scenario — same scenario
GIT_90 used for its own rowSpan measurements): I toggled `message()`
between the real empty-string case and a forced non-empty string via a
temporary source edit + Vite HMR (no full page reload, so scroll and
viewport state stayed identical across the A/B — a plain DOM-splice probe
gave contaminated numbers here, traced to `.panel-body > .card-head`'s
`margin-bottom: auto`, see below), then measured `getBoundingClientRect()`
on the Running line, the tool picker, the tools table, the Steps caption
and the Steps list before/after, restoring the source between reads.

Result: with the card at the Lab's preview height (424px, taller than this
scenario's tight content floor), toggling the message moved **only** the
Running line's own top position, by exactly -22px; the tool picker, table,
Steps caption and Steps list did not move at all (0px delta, every one).
That's not the reservation quietly surviving — it's
`.panel-body > .card-head { margin-bottom: auto }` (app.css:4255-4263, an
existing, unrelated mechanism `contentRowSpan()` depends on to keep a
card's own free space out of its measured floor). Whenever the card has
slack above its tight content floor, that auto margin absorbs a size
change right below the header, and nothing visible shifts.

**At the card's own measured floor (rowSpan 102, i.e. no slack left for
that auto margin to give)**, there is nowhere for the 22px to go but down:
the tool picker, table and step list would shift down by 5.5u when the
message appears, and back up when it clears — bounded, one-time per
transition, not continuous jitter. This is exactly what the old reservation
always cost the ordinary case, now spent only on the message's own
appearance/clearing.

**Judgement:** not material enough to withhold, and I did not add a
mitigation beyond what's here. Tracing where `message()` can actually
change (`svc.store.error()` is set only inside the once-per-connection load
effect at mount, `compose/services.ts:889-913` — not per tool-switch;
`svc.problem()` is set only by `rank()`, a synchronous, non-moving compute
call, `compose/services.ts:1140-1161`) shows neither source fires
concurrently with the carriage actually moving in the normal one-step-at-a-
time workflow this card watches. The reservation's stated purpose — not
jumping under a running measurement — is not being reintroduced in the case
that motivated it. Gabe's own #99 call ("remove it... do not relitigate")
plus GIT_90's precedent (identical trade, verified rather than assumed) is
what I followed; I'm reporting the bounded worst case rather than shipping
it silently, per the parent issue's requirement 3, but not proposing an
alternative because the worst case doesn't reach the failure the
reservation existed to prevent.

## Revision (round 2)

Triggered by review + Gabe's decision. What was wrong in round 1, corrected
here rather than left standing:

- **The frequency claim was inverted.** I measured the "nothing moves"
  behaviour at the Card Lab's 424px preview height and reported it as the
  common case, with the floor-only 5.5u shift as the rare edge. The review
  traced the real sizing mechanism: the composed screen is a CSS grid where
  `shell/PanelCanvas.tsx:18-19` sets `grid-auto-rows: var(--u)` and
  `shell/panelCanvas.ts` places every card with `grid-row: span rowSpan` —
  so a card's rendered height is exactly `rowSpan × --u`, never more, unless
  an operator has manually enlarged it. I had set `rowSpan: 102` TO the
  no-message floor, so the shipped card has zero slack by construction. The
  5.5u shift was therefore the DEFAULT for every operator who has not
  resized the card, not the rare case I reported.
- **I missed a reconnect path.** `svc.store.error()` is set inside
  `compose/services.ts`'s revision effect, which resets on every reconnect
  (`connected()` flipping back true), not only once at mount. A network
  drop does not stop the carriage — this is exactly the "message changes
  while the machine is being watched mid-measurement" case the original
  reservation existed for, and round 1's report said it couldn't happen.
- Both corrections concern the RISK CHARACTERISATION, not the mechanism:
  the CSS/JSX I shipped in round 1 did what I said it did. The report
  presented an inverted frequency claim as "verified negligible," and that
  is what changed Gabe's answer.

**Gabe's decision:** move `.shp-msg` after the step list, so nothing on the
card follows it — removing the movement entirely rather than trading one
placement's dead space for another's shift.
