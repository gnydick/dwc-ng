## 1. What was wrong, traced

### A — `persistCache` wrote the origin-global record from one instance's memory

`persistCache` (`config/store.ts`) called `writePersonCache(person, meta.dirty,
meta.snapshots)`. `meta.snapshots` is seeded once at `createConfigStore` from the cache
present AT CONSTRUCTION and never re-read, so an instance built before a save persisted
its stale (usually empty) list over the newer record. Captured stack from the owner's
browser: `writePersonCache ← persistCache ← commit ← apply ← setAxisRole ←
SettingsCards.tsx:60`.

The unstated assumption riding along with the `whole-cache-write` invariant was not
"overlay/dirty/snapshots are written together" (true, and preserved) but "the writer's
copy is the only copy" (false the moment a second tab exists).

### B — every geometry write reported an operator edit

`persist` in `shell/panelCanvas.ts` ended with an unconditional `onLayoutChange?.()`,
and `ComposedScreen.tsx:185` passes `markLayoutDirty` as that callback. Two of the seven
callers of `persist` are not operator acts at all: `ensureSlot` and `removeSlot`, driven
by ComposedScreen's composition-sync effect (`ComposedScreen.tsx:204-210`), which runs
whenever the canvas and the composition disagree — including while the screen is being
brought up to date at boot.

The reconcile route must be silent rather than merely quieter, and this is checkable:
the config edit that changes a screen's membership goes `setScreenCard`
(`config/store.ts:682`) → `apply` (`:500`) → `commit(next, true)` (`:391`), which has
ALREADY set the flag before the canvas hears about it. So the canvas reporting it again
can only double-count; at boot, where nothing was edited, it is simply false.

### Honest correction to the ticket's premise for B

**I could not reproduce a boot-time dirty flag on the mock at `25c1d8c`.** Instrumented
`markLayoutDirty` with a stack capture, ran a fresh profile through: first boot, three
reloads, a walk of all nine composed routes, an edit-and-save cycle, and a canvas store
hand-seeded with a stale slot id. `markLayoutDirty` was called **zero** times in every
case, and `dwc-ng.person` never went `dirty:true`. The reason is structural:
`growToDefaults` builds canvas state ONLY from `defaults` (= `slotsOf(composition())`
captured at construction), so at boot `ensureSlot` early-returns for every slot and
`removeSlot` finds nothing — a junk id injected into storage is dropped by
`growToDefaults`, not passed to `removeSlot`. The reconcile writes fire only when the
composition changes AFTER the canvas mounts.

So the ticket's diagnosis names the right mechanism and the right call path, but the
trigger the owner hit is a composition change arriving after mount (a screen import, a
revert/adopt, a reset-everything, a second `loadFromMachine`), not a plain reload of the
current build. The fix stands either way — requirement 4 is definitional, and every one
of those routes reports unsaved work that the config layer has already reported — but
**the owner should confirm his symptom is gone rather than my assuming it, because I
never saw it.** If it survives, the next thing to instrument is what makes
`composition()` change after `configLoaded()`.

## 2. The fixes, and the rung each actually sits at

### A — `config/person-cache-snapshots-only-grow`, rung 6

`writePersonCache` **no longer takes a history**. Its third parameter is `contribute`
(default `[]`) — what THIS call brings — and the `snapshots` field of the stored record
is computed inside it:

```ts
const snapshots = mergeSnapshots(readStoredSnapshots(), contribute);
```

There is no argument any caller can pass, correct or otherwise, that expresses "the
stored history is exactly this list". `persistCache` now passes nothing; `snapshot()`
passes the single entry it just minted; the v2→v3 migration passes the legacy entries.
`mergeSnapshots` unions by id, orders by `takenAt` (stable sort, so same-millisecond
saves keep the order they arrived in — `revert(i)` is indexed by that order), and keeps
the newest `MAX_SNAPSHOTS`. It is commutative and idempotent, so two tabs writing in
either order converge rather than racing.

**Rung 6, not 7**, and the reason is nameable: `writePersonCache` is module-private and
the sole `setItem(CONFIG_CACHE_KEY, …)` in the program, but nothing in the type system
stops a future module reaching for the raw key. That is what the sole-writer scan in
`test/config-person-cache-merge.test.ts` pins — a walk of all of `packages/ui/src`
failing on a second writer of `CONFIG_CACHE_KEY` or the literal `"dwc-ng.person"`.

### Requirement 2 — `config/open-tab-sees-other-tabs-history`, rung 6

`createConfigStore` subscribes to `storage` (guarded on `typeof window`, torn down via
`onCleanup`) and re-hydrates through the SAME `mergeSnapshots`, so a tab's in-memory
list and the record on disk cannot disagree about which entries exist. **Snapshots only:**
`overlay` and `dirty` are this instance's own unsaved work, and adopting another tab's
copy would discard an edit the operator is still typing. A `storage` event never fires
in the document that caused it, so the handler is only ever another tab talking.

### B — `shell/only-an-operator-gesture-reports-unsaved-work`, rung 6

```ts
export type LayoutOrigin = "operator-gesture" | "composition-reconcile";

const persist = (next: CanvasState, origin: LayoutOrigin): void => {
    setState(next);
    keys.set("layout", serializeCanvas(next));
    if (origin === "operator-gesture") onLayoutChange?.();
};
```

`origin` has **no default**, so a geometry write that never decided whose act it was does
not compile. `onLayoutChange` is named at exactly one line in the program. Seven call
sites, all annotated: two `composition-reconcile` (`ensureSlot`, `removeSlot`), five
`operator-gesture` (group drop, single drop, resize drop, `adoptLayout`, `resetSlot`).

**Rung 6, not 7**: the two origins are string literals a call site could still pick
wrongly, and picking `composition-reconcile` for a drag would make a rearranged screen
unsavable — the exact failure the ticket forbids. `test/layout-dirty-origin.test.ts`
scans every `persist(` call site by line, requires an origin literal on each, requires
exactly two reconciles, requires `onLayoutChange` at one line, and requires that line to
sit behind `origin === "operator-gesture"`.

**Enumerated, per the class-ruling rule — the geometry writers NOT on this route:**
`reset()` (`panelCanvas.ts:1978`) REMOVES the layout key rather than writing one and has
never notified; the construction-time settle write (`:1455`) is a deterministic repair
and deliberately calls `keys.set` directly; `writeCanvasState` (`:2047`) is the
unmounted-screen import writer and has no controller to notify. All three predate #120,
none can express a notify, and none is changed by it.

## 7. Concerns for the owner

1. **B's symptom was never reproduced on this build** (§1). The fix makes requirement 4
   true by construction and closes every route that can report a phantom edit, but I
   cannot claim it fixes the exact thing you saw, because I never made it happen.
   Please check on the mock whether a plain reload still flips to "Unsaved changes"; if
   it does, the remaining question is what makes `composition()` change after
   `configLoaded()` in your session.
2. **The history can now only grow.** Nothing in the program can shorten it — which is
   the point, but it also means a future "clear backup history" needs a new, explicit
   route through `writePersonCache`, not a caller passing a shorter list.
3. **Cross-origin histories are still separate** (`localhost:5187` vs `127.0.0.1:5187`
   vs the board's own origin). Unchanged by this ticket and a genuinely different
   problem — the person cache is origin-global, and the origins differ.
4. `origin` is a string literal union, so a future call site can still label a drag as a
   reconcile. The compiler forces the choice but not the right one; the call-site scan is
   what catches a wrong one.
