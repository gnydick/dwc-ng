## The picker (markup)

```tsx
<div class="shp-active">
	<span class="shp-cap">Tool</span>
	<div class="shp-tool-pick" role="group" aria-label="Tool being tuned">
		<For each={tools()} fallback={<button class="shp-pick shp-tool-chip" disabled>{NONE}</button>}>
			{t => (
				<button
					class="shp-pick shp-tool-chip"
					aria-pressed={svc.tool() === t.number}
					disabled={tools().length <= 1}
					onClick={() => svc.setTool(t.number)}
				>
					T{t.number}
				</button>
			)}
		</For>
	</div>
</div>
```

CSS: reused `.shp-tool-pick`/`.shp-tool-chip` (already existed for the Sweep
card's identical picker — its comment even anticipated this: "aria-pressed is
what the status card's picker uses"). One new rule added:
`.shp-tool-chip:disabled { opacity: 0.4; cursor: not-allowed; }`.

**Disabled-parity verification** (three methods):
1. Direct DOM measurement in a live render: `.shp-active` row height was
   24px identically with 4 real chips, with 3 chips removed + 1 disabled
   (simulated 1-tool), and with 0 chips + the disabled placeholder (simulated
   0-tool).
2. A source-level probe (`tools().slice(0,1)` / `.slice(0,0)`) run against the
   real component in Card Lab (`shaping-measured` scenario): 1-tool gave one
   disabled chip "T0", row 24px; 0-tool gave one disabled chip "—", row 24px;
   restored gave 4 enabled chips, row 24px.
3. The same probe repeated **live against the real Shaping screen, connected
   to mock-duet's bundled toolchanger capture** (see UAT below) — same result,
   plus confirmed the table's two distinct fallback strings fire correctly
   ("no tools on this machine" for 0 tools; "T1 is not a tool on this
   machine" for a mismatched selection).

## Comment rewrite (`compose/services.ts:391-401`)

```
The results themselves come off the SD card through the store's single
reader (shaping/store.ts `results-persist-through-one-writer`), loaded for
every tool the machine reports rather than only the selected one — even
though the status card's own table now shows just the one row `tool()`
names (GitHub #90; the all-tools table this paragraph used to justify is
gone). The reason to keep loading all of them is the PICKER, not the
table: it is one click, on the status card, and every one of the other
seven cards is `tool()` alone — a switch that then had to wait on a
download would put a fetch, and a fetch's own failure mode, on the single
gesture this screen exists to make cheap. Paying for every tool once, up
front, is what lets the picker cost nothing per click; `loaded` below is
what keeps that a once-per-tool-per-connection cost rather than a repeat
of it.
```

I deliberately did **not** change the eager-load-all-tools *behaviour* itself
(`compose/services.ts:843-859`) — only its stated rationale. The old
rationale ("the table would lie") no longer applies; the new one (instant,
request-free tool switching for the other seven cards) is a real, independent
justification for keeping the same code, so no behavioural change was needed
there.

## Sweep: what was removed, and what stayed

group (`.shp-tool-pick`/`.shp-tool-chip`, writing `svc.setTool`), and the

step readout exactly as they were. The unused `tools` memo that fed the `<For>`
came out with it.

**Geometry**: `.shp-sweep-bar`'s row height is declared on the ROW itself
(`min-height: calc(8 * var(--u))`, shared with `.shp-batch`/`.shp-decay-filter`
— see app.css ~5008), independent of what is inside it. Measured via Card
Lab's `contentRowSpan()` audit against `shaping-measured`, **before and after**
removing the picker: **119 rows, identical, 0 delta** ("no child moved", stable
across 3 probes in the sense that both versions report the same number — see
Concerns below for a pre-existing, unrelated instability this surfaced).

separate, unrelated drift (see Concerns).

**Was there a hole?** No. `armed`/`save`/`arming` (the save-arm logic) were
untouched — they already read `svc.tool()` fresh inside `save()` rather than
trusting a snapshot (`if (armed() === svc.tool()) { fire } else { re-arm }`),
so a tool switch initiated elsewhere on the screen was already safe against
this card's arm going stale-and-firing-wrong; it can only re-arm, never
mis-fire. Verified live (see Falsification).

**What happens to a stale arm on tool change?** Tested directly (see
Falsification): arming Decay's Save for T3, then switching to T0 via the
picker, leaves the confirm sentence and button label showing the STALE armed
tool (T3) for one render — but clicking "Confirm" in that state does **not**
write to T3. `save()`'s own guard (`armed() === svc.tool()`) fails (3 ≠ 0), so
the click only re-arms for T0; a second click is required to actually save,
and it correctly targets T0. **Safe by construction, not stale-proof
cosmetically.** This exact pattern (local `armed` number, compared fresh
against the live tool each click, no reset effect) is the SAME one already in
Sweep's save and Capture's run/save arms, all pre-existing and all sharing the
same one-click cosmetic staleness. Left as is rather than inventing a new
"disarm on tool change" behavior found nowhere else on the screen — flagged
as an optional, screen-wide follow-up below rather than a round-2-only patch.

# Fix round 3 (2026-08-26) — cant-break-by-design: delete the duplicate, don't guard it

Gabe, invoking `cant-break-by-design`: "it shouldn't be possible to mismatch
tool identification in the same active code." Round 2's review proved the
existing `armed().tool !== svc.tool()` comparison never let a mis-save
through — but the mismatch was still REPRESENTABLE (two copies of "which
tool" in the running code, kept apart only by a comparison someone had to get
right). This round removes the second copy and wires disarm-on-tool-change
through the two mechanisms already proven: `svc.setTool` (sole write site,
round 1) and `control/armed.ts`'s global `disarmers` (sole way an arm is
minted, existing `escape-disarms` invariant) — rather than inventing a third.

## The mechanism

`control/armed.ts` gained one export, `disarmAll()` — the exact loop the
Escape listener already ran, factored out so a second caller doesn't have to
re-walk `disarmers` itself. The Escape listener now calls it too, so this is
a refactor of the EXISTING mechanism, not a new one beside it.

`compose/services.ts`'s `setTool` calls `disarmAll()` unconditionally, every
call, as its fourth line — no `next !== tool()` guard.

```ts
const setTool = (next: number): void => {
	setToolNow(next);
	setCapturePick(null);
	setCandidateIndex(0);
	disarmAll();
};
```

## `@invariant tool-change-disarms` — rung 6

Declared beside `setTool` in `compose/services.ts` (full text there and in
`docs/invariant-register.md`, regenerated — see below). Rung assigned from
the mechanism:

- `setTool` is the only member of `SERVICES.shaping`'s returned object that
  writes `tool` — `setToolNow` is a closure-local `const`, never returned, so
  a card literally cannot call it; TypeScript would refuse the property
  access. That is a compile-time fact, not a grep result.
- `disarmAll()` iterates the same `disarmers` Set that `createArmed` is the
  ONLY way to join — `test/armed.test.ts` already walks the whole source tree
  for a raw `[armed, ...]` signal that bypassed it, and that walk is
  unaffected by this round (still green).
- Combining the two: any card that arms via `createArmed` — which is every
  two-step control in this codebase, by the walk above — is disarmed on a
  tool change by construction of calling `createArmed`, not by a comparison
  someone remembered to write or a convention someone could forget.

Not claimed as rung 7/8: nothing makes it a compile error to write a NEW arm
payload that smuggles a tool number back in — a future author could still
type `{ kind: "save", tool: number }` again; they just wouldn't need to, and
nothing in the type system refuses it. Rung 6 (a runtime choke point,
mechanically enforced by the existing walk plus this round's test) is the
honest number, not 7.
